# ПОС — Преподавательская Оценка Студентов

Консольный модуль оценивания студентов: студенты, рубрикатор критериев с весами, оценки, итог и его экспорт. Построен на доменной модели в духе DDD, слоёной архитектуре Clean Architecture и паттернах GoF.

## Как запустить

Нужен .NET 10 SDK. Все команды — из корня решения.

```
dotnet run --project src/Pos.Console              # интерактивное меню
dotnet run --project src/Pos.Console -- --demo    # демонстрация сквозного сценария ТЗ
dotnet test                                       # юнит-тесты
```

Данные хранятся в JSON рядом с исполняемым файлом: `src/Pos.Console/bin/Debug/net10.0/data/`. Демо пишет в отдельную папку `data-demo` и при каждом запуске начинает с чистого листа, рабочие данные не трогает.

**Демо** прогоняет сценарий из ТЗ: завести студентов и критерии → выставить оценки → получить итог → экспортировать итог. По ходу он пытается нарушить каждое правило домена и показывает, что модель отказывает.

## Архитектура: Clean Architecture

```
Pos.Console ──────► Pos.Application ──────► Pos.Domain
     │                                          ▲
     └────────────► Pos.Infrastructure ─────────┘
                    (реализует порты домена)
```

| Слой | Проект | Отвечает за |
|---|---|---|
| Domain | `Pos.Domain` | правила предметной области |
| Application | `Pos.Application` | сценарии: загрузить → вызвать домен → сохранить |
| Infrastructure | `Pos.Infrastructure` | JSON-файлы, CSV/JSON-экспорт |
| Presentation | `Pos.Console` | ввод, вывод, сборка графа зависимостей |

**Зависимости направлены внутрь.** В `Pos.Domain.csproj` нет ни одного `ProjectReference`, домен не знает про файлы, консоль и сериализацию. Интерфейсы хранилища и экспорта объявлены в домене (`Ports/`), реализации лежат в инфраструктуре, фасад работает только с интерфейсами.

**Composition root — `Program.cs`.** Здесь собирается граф зависимостей, включая инфраструктуру. Чтобы заменить базу данных, понадобится новая реализация портов и одна строка в `Program.cs`.

**Про термины.** DDD даёт то, что есть в модели — Entity, Value Object, Aggregate, Repository, Domain Service. Clean Architecture — слои, и как они расположены друг к другу.

**Всё синхронно.** Единственный пользователь и локальные файлы, асинхронность добавила бы сложности без выигрыша.

## Доменная модель (DDD)

### Единый язык

| Термин | Класс |
|---|---|
| студент | `Student` |
| критерий | `Criterion` |
| рубрикатор | `Rubric` |
| оценка | `Evaluation` |
| балл | `Score` |
| вес | `Weight` |
| итог | `FinalScore` |
| ведомость (мой термин: все оценки одного студента) | `Gradebook` |

### Entity и Value Object

| | Тип |
|---|---|
| `Student`, `Rubric`, `Gradebook` | Entity, корни агрегатов |
| `Criterion`, `Evaluation` | Entity внутри агрегатов |
| `StudentId`, `CriterionId` | VO, `readonly record struct`: перепутанные Id ловит компилятор |
| `StudentName`, `Weight`, `Score`, `FinalScore` | VO, `record`: каждый проверяет себя сам |

**Пример различия.** `Evaluation` — сущность, потому что ТЗ требует оценку *исправлять*: после исправления это та же оценка с другим баллом, а не новая. `Score` — значение: два балла «8» взаимозаменяемы, и при исправлении балл не меняют, а заменяют новым. Идентичность `Evaluation` локальна — её задаёт пара «ведомость + критерий», поэтому отдельный Id не заводился.

VO со строками и числами объявлены как `record`, а не `record struct`: у структуры есть неявный конструктор без параметров, и `default(StudentName)` обошёл бы проверку имени.

### Агрегаты

| Агрегат | Корень | Внутри | Репозиторий |
|---|---|---|---|
| Студент | `Student` | — | `IStudentRepository` |
| Рубрикатор | `Rubric` | `Criterion` | `IRubricRepository` |
| Ведомость | `Gradebook` | `Evaluation` | `IGradebookRepository` |

Один репозиторий на агрегат, а не на сущность.

**Почему границы проведены именно так.** Рубрикатор — отдельный агрегат, потому что у него есть правила (сумма весов, уникальность имён), которые нельзя проверить на одном критерии. Ведомость — отдельный агрегат, потому что у неё есть правило (мой инвариант): не больше одной оценки на критерий.

**Ссылки между агрегатами — только по Id.** `Evaluation` хранит `CriterionId`, а не объект `Criterion`. Рубрикатор передаётся в методы ведомости аргументом (`gradebook.Grade(rubric, ...)`), а не хранится в ней, иначе ведомость держала бы устаревшую копию.

### Инварианты

Из ТЗ: балл не выходит за пределы критерия — проверяет `Criterion.ValidateScore`, потому что максимум знает только критерий; оценка ставится только по критерию из рубрикатора — проверяет `Rubric.GetCriterionById`; итог согласован с набором оценок — итог нигде не хранится и всегда считается заново из актуальных оценок.

Мои: не больше одной оценки на критерий (`Gradebook`), сумма весов ровно 100% и уникальные имена критериев (`RubricBuilder`), непустые имена, вес в (0; 1] и балл ≥ 0 (сами VO). В `Gradebook.Grade` встречаются три правила сразу: рубрикатор проверяет, что критерий существует, ведомость — что дубля нет, критерий — что балл в диапазоне.

Правило «одна оценка на критерий» следует из определения оценки в ТЗ как факта *«этому студенту по этому критерию поставили такой балл»* и из требования *«исправить или отменить»*. Ведомость хранит оценки в словаре с ключом `CriterionId`, хотя тот же Id есть и внутри `Evaluation`. Дублирование сознательное: словарь делает дубль невозможным структурно и даёт поиск по критерию за O(1), а рассогласоваться ключ и значение не могут, потому что вставка идёт только в двух методах ведомости. Исправление — отдельный метод `Regrade`, а диалог «перезаписать? y/n» живёт в консоли.

Сумма весов строгая: веса хранятся как `decimal`, поэтому 0.4 + 0.3 + 0.3 равно 1 точно. Следствие — рубрикатор неизменяем и меняется только пересборкой целиком. Для удобства пользователь вводит веса в процентах, целыми числами — так их привычно называть («домашки — 40%»), и не нужно думать о десятичном разделителе. Домен при этом хранит доли, перевод выполняет фасад (`Weight.FromPercent`). Итог считается только по полному набору оценок: если чего-то не хватает, расчёт перечисляет недостающие критерии, а не подставляет молча ноль.

### Domain Service

`FinalScoreCalculator` считает итог, которому нужны и оценки из ведомости, и веса из рубрикатора, поэтому он не принадлежит ни одной сущности. Итог — `Σ (балл / максимум × вес)`, доля от 0 до 1; `FinalScore` хранит её и выводит из неё 10-балльную оценку с двумя знаками и целую, так что рассогласоваться они не могут. Сервис без состояния, ничего не грузит и не хранит, и не статический, чтобы попасть в фасад через DI.

### Создание и восстановление объектов

У каждой сущности единая точка создания: для `Student` — фабричный метод `Create`, для рубрикатора — `RubricBuilder`, поскольку его инвариант проверяется только на полном наборе. Восстановление из хранилища вынесено в `Restore`, который принимает готовые идентификаторы и заново проверяет инварианты: файл мог быть повреждён. Конструкторы `Criterion` и `Evaluation` — `internal`, поэтому критерий существует только в составе валидного рубрикатора, а оценка — только внутри ведомости.

Наружу коллекции отдаются только для чтения. Порядок критериев значим (это порядок столбцов отчёта), поэтому внутри `Rubric` — `OrderedDictionary`.

### Чего в модели сознательно нет

- **Интерфейсов на сущности** — у каждой одна реализация, интерфейсы в домене только для портов.
- **Базового `Entity`** — сравнение сущностей между собой в сценариях не встречается, а наследование ради единообразия было бы overengineering.
- **Наследования** — доменные классы `sealed`.
- **Группы студента, ревьюера, курса** — этих сущностей нет в ТЗ.

## Паттерны GoF

**Builder (порождающий) — `RubricBuilder`.** Сумма весов не может быть 100%, пока критерии добавляются по одному, поэтому проверка набора нужна в момент завершения сборки. `Add` проверяет то, что проверяемо сразу (уникальность имени), `Build` — сумму весов.

**Фабрика (порождающий) — `Gradebook.Grade`.** Оценку можно создать только через этот метод: конструктор `Evaluation` закрыт. Перед созданием метод проверяет, что критерий есть в рубрикаторе, балл не выходит за его пределы и оценки по нему ещё нет. Отдельный класс-фабрика не нужен: ведомость сама создаёт свои оценки.

**Facade (структурный) — `PosFacade`.** Одна точка входа для всех сценариев: добавить студента, выставить оценку, посчитать итог, экспортировать. Меню не нужно знать, какие данные загрузить и в каком порядке вызвать домен, — оно просто вызывает один метод фасада. Поэтому те же методы без изменений используют демо и тесты. Здесь же сортировка студентов по фамилии, чтобы меню и экспорт шли в одном удобном порядке.

**Template Method (поведенческий) — `ReportExporter`.** Экспорт в любой формат идёт по одним и тем же шагам: собрать текст, создать папку, записать файл. Базовый класс выполняет эти шаги сам, а CSV- и JSON-экспортёры пишут только то, чем отличаются, — как собрать текст.

Рассмотрены и отклонены: Strategy для итога (формула одна), Decorator для округления (это представление, `FinalScore` уже отдаёт обе формы), отдельная фабрика экспортёров (решил не усложнять).

## Хранение и экспорт

**Модели хранения отделены от домена.** В `Persistence/Models` лежат простые записи, которые повторяют структуру JSON-файлов: Guid вместо `StudentId`, число вместо `Weight`. В доменные объекты и обратно их переводят мапперы. Анемичность тут осознанна: это формат файла, а не предметная область.

**Репозитории читают файл один раз при старте** и дальше работают с кешем в памяти, `Save` сразу перезаписывает файл. Они зарегистрированы синглтонами, чтобы на программу был один кеш на файл. `GetById` каждый раз собирает новый объект, поэтому изменение снаружи не попадёт в кеш в обход `Save`.

**Выбор формата экспорта.** Формат определяется расширением файла, который указал пользователь: `.csv` — таблица для Excel, `.json` — данные для других программ. Маршрутизацию выполняет `ExtensionReportExporter`: фасад зависит от одного порта `IReportExporter` и не знает о форматах. Добавление нового формата — новый наследник `ReportExporter` и одна строка в словаре диспетчера; домен, фасад и консоль не меняются.

В CSV строка на студента и столбец на критерий в порядке рубрикатора, в заголовке — максимальный балл: `Домашки (из 10)`.

## Тесты

19 тестов xUnit: инварианты рубрикатора и оценок, расчёт итога на известных числах и с округлением, отказ при неполном наборе, сценарии фасада. Тесты фасада подменяют репозитории реализациями в памяти (`Fakes/`) — фасад зависит от интерфейсов, поэтому ни файлы, ни изменения кода не нужны.
